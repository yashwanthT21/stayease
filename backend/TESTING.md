# Backend Testing

Unit tests for every backend module, written with **JUnit 5 + Mockito + AssertJ**
(all three come from `spring-boot-starter-test`).

## How to run them

```powershell
# one module
cd backend\stayease-backend ; .\mvnw.cmd test

# every module
foreach ($m in 'stayease-backend','property-service','notification-service','api-gateway') {
  Push-Location "backend\$m" ; .\mvnw.cmd test ; Pop-Location
}
```

No database, no running services, no Docker — see "Why unit tests" below.

## Why unit tests (and not integration tests)

Each test replaces the repository — and any other service the class talks to — with
a **Mockito mock**, then asserts on what the class under test decided. That means:

- **No database.** The tests don't need MySQL running, so they work on any machine
  and in CI.
- **They test OUR logic, not Spring's.** `findByOwnerId` is generated by Spring
  Data; there's nothing of ours to verify in it. The interesting code is the rules
  around it, and that's what's tested.
- **They're fast** — the whole suite is a few seconds, so it's cheap to run often.

The trade-off is honest: these tests would not catch a wrong column mapping or a
broken Flyway migration. That's what an integration test (`@SpringBootTest` +
Testcontainers or H2) would be for, and it's the natural next step.

## The rules these tests actually pin down

Not every test is a getter check. The ones worth talking about:

**Money and maths are server-owned.** A client sends facts, the server computes
totals, so a total can always be trusted:
- `ReservationServiceImplTest` — `nights` is derived from the dates, and
  `totalAmount = baseAmount + cleaningFee + serviceFee`.
- `OwnerStatementServiceImplTest` — `netPayout = grossRevenue + cleaningRevenue −
  platformFee − managementFee − maintenanceCost`, including the negative case
  (a quiet month with a big repair bill) and missing amounts counting as zero.
- `GuestReviewServiceImplTest` — the overall score is the average of the scores
  given, so a guest can't post a 5-star average with 1-star details.

**Nobody can act on the past.** `AvailabilityCalendarServiceImplTest` proves a date
before today is rejected on both create and update, that a future row can't be
dragged backwards into the past, and that *today itself* is still editable. Because
booking approval goes through that same endpoint, this is what actually stops a
guest booking a night that has already gone — the greyed-out calendar cells in the
UI are a courtesy, this is the guarantee. `ReservationServiceImplTest` adds the
same rule at the booking end.

**Scopes can't be widened.** `PropertyServiceImplTest` checks that passing both
`ownerId` and `managerId` *narrows* the query (`findByOwnerIdAndManagerId`) rather
than letting `ownerId` win — if `ownerId` won, one manager could read another
manager's properties.

**State a user shouldn't control stays put.** `GuestProfileServiceImplTest` shows a
guest saving their own profile keeps their verification tier, review score and
booking count, while an admin who *does* send a verification status can change it.

**Approval is a real state machine.** `ReservationServiceImplTest` covers
approve/reject only working on a `PENDING` request, and approval holding the nights
in property-service *before* confirming — so an approval can never double-book.

**Cross-service side effects happen, but never break the main action.**
The notification hand-off is verified with Mockito (`verify(notificationClient)…`):
a booking request notifies the property's manager, falling back to the owner when
none is assigned; approve/reject notifies the guest; a new review notifies owner
and manager, deduplicated when they're the same person. `GuestReviewServiceImplTest`
also proves a review is still saved when property-service can't be reached.

**The gateway rejects bad tokens at the edge.** `JwtServiceTest` mints real tokens
and checks that a valid one parses, and that a forged signature, an expired token,
and a garbage string are all refused — which is the whole argument for a stateless
JWT: the gateway decides without calling IAM.

**Two regression guards for bugs we actually hit.**
- `NotificationServiceImplTest.getAllFiltersByStatusAlone` — a status-only filter
  used to fall through to `findAll()` and silently return everything.
- `CheckInRecordServiceImplTest` — an operator's chosen status appeared to be
  ignored. The cause turned out to be in the Angular form, not the backend, but
  these tests pin the server side of the contract so next time the answer is a test
  run instead of a guess.

## Frontend tests

There are also 10 Angular tests (`npm test` in `frontend/`) covering the check-in
and check-out forms — `check-in.spec.ts`, `check-out.spec.ts`. They drive the real
DOM and assert on the HTTP request body, which is how the select-binding bug above
was actually pinned down.
